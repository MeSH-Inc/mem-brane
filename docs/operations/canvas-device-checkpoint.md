## iPhone protocol diagnosis and keyboard subset

The resumed iPhone run mounted all 500 cards and confirmed a secure foreground page. SafariDriver acknowledged `Automation.performInteractionSequence`, then never answered its next `Automation.resolveBrowsingContext` request. Session deletion timed out too. This protocol sequence matches [WebKit issue 322937](https://bugs.webkit.org/show_bug.cgi?id=322937), reported for iOS automation. Restarting Safari on the phone recovered the connection. This is evidence of an automation failure, not proof of an application gesture failure.

The checked-in iOS Safari branch now avoids the affected Actions endpoint. Element Send Keys delivered trusted key events for selection, arrow-key geometry changes, cancellation and retry. At each delay a fresh scene restores all four streams; a second card persists while the first response stays held, cancellation progresses, and the first card's newest geometry survives the conflicting response and explicit retry. Both delays passed all five assertions. The report explicitly labels this keyboard subset and the unverified inputs. No input-latency samples were armed, so its frame intervals are observations only and do not establish a responsiveness budget. Focus was set through the DOM; hardware keyboard focus traversal is still pending.

Separate element-click and text-entry probes returned successful protocol responses without the expected state changes; those calls were not counted as passes. Native gesture validation is moving to XCUITest input with web-view observation. Appium 3.7.0, XCUITest driver 12.12.1 and WebDriverAgent 16.12.7 are prepared in ignored `artifacts/stress/device/ios-tools/`. The runner compiled unsigned successfully. Its signed launch failed because Xcode reports **No Accounts** and has no development provisioning profile for the runner. The local signing certificate alone cannot complete provisioning. Xcode account sign-in is the remaining prerequisite; no native runner was installed.

## Reproduction and remaining work

The [verification guide](../interaction-verification.md#repeatable-device-automation) documents HTTPS setup and the `test:device:android` / `test:device:safari` commands. Both run the two save delays and fail when an assertion or driver command fails. The iOS Safari command covers the verified keyboard subset and emits `ios-safari-keyboard-results.json`; it does not claim native touch or text-entry coverage.

Sign in to the Apple developer account in Xcode → Settings → Accounts, provision the prepared native runner, and finish the iPhone gesture/text checks at both delays. Then perform the guide's human-input matrix: trackpad inertia and pinch; mobile selection handles and long press; one-finger continuation after pinch; rotation and software-keyboard transitions in Canvas and Focus; hardware keyboard traversal. Keep a screen recording and metric export for any failure. Trace and fix the responsible input, rendering or persistence boundary only when a reproduction demonstrates a problem; the [trace checkpoint](interaction-trace-checkpoint.md) does not support changing the renderer based on the previous headless gaps.
